# 正文与失败原因校验

按四层判断：请求是否完成 → 返回的是不是目标页面 → 有没有主体内容 → 覆盖了哪些部分。每一层都保留可定位的证据。

## 边界情况

| 观察到的情况 | 处理 |
|---|---|
| 文章/帖子讨论 404、Page not found | 结合标题、主体和平台结构判断；不能仅命中关键词就判错误页。 |
| HTTP 200，但只有验证码、登录或拒绝访问提示 | unresolved；若还含真实预览，最多 partial 并注明范围。 |
| 重定向到首页、其他日期或另一篇文章 | 不自动成功；核对内容身份。 |
| 长导航、推荐列表、站点页脚 | 长度不能证明正文存在；没有主体则 unresolved。 |
| 只有标题、作者、账号资料、点赞数 | 元数据，不是文章或帖子主体；保留 partial 或 unresolved 的具体依据。 |
| 视频字幕、描述、频道列表、图片 caption | 标记实际取得的文字范围，不能等同完整视频/图片内容。 |
| PDF 字节被错误解码为文本 | unresolved；解析 PDF，扫描件另做 OCR，记录 OCR 范围。 |
| 短而完整的回答/通知 | 自动短文本阈值仅提示 review；可基于实际上下文人工确认。 |
| 付费预览或“继续阅读需登录” | partial，不把预览长度当全文覆盖证据。 |
| 批量请求 HTTP 200，item 内有 parse_error | 该 item 失败；其他成功 item 正常保留。 |

脚本阈值是筛查启发式：通用正文少于 350 字符、结构化主体少于 80 字符进入 review；不是完整性标准或网页质量标准。结构化帖子主体存在时，避免将帖内错误词误判为站点错误，但仍须检查是否抓错内容。

## 人工检查与导出

检查 selected attempt 的原始响应及文字文件，核对 URL 身份、主体边界、日期/版本和覆盖范围。用 review-file 保存 attempt_id、校正状态、原因和 evidence_note；原始自动判定与其他尝试都应保留。文件存在本身不代表人工核验完成。

批量交付应明确自动筛查与人工检查范围；按状态、通道和域名抽查，并重点检查跳转、错误提示、短内容、PDF、社交和媒体页面。没有逐页核验时不要宣称全部正文完整。抓取成功也不代表事实准确或 PQ 高。

## 失败归因

优先列出直接观察到的证据：目标 HTTP 404/410、服务 API 404、验证码、登录限制、DNS/TLS/连接错误、空响应、解析错误、页面身份不匹配、账户/配额报错、待完成任务。不要把这些统称“网页不存在”或“无法访问国外网站”。

HTTP 状态所在层级、原始错误、通道、时间、任务 ID 都要可回查。主因分类用于互斥统计，次要证据仍保留；多次尝试的错误不一定有同一根因。未知根因明确写未知。厂商账户报错不是账户事实证明，需与控制台或支持证据核对。

分别统计输入出现次数、去重 URL、各最终状态，以及仍在运行或提交结果未知的任务。重试后更新最终结果但不抹掉旧证据；不要把尚未请求的条目算作抓取失败。
