# 查询理解与上下文规则

## 1. 查询、解释和意图

查询是用户输入的文字、语音、图像或其他搜索表达；缺少理解图像／语音所必需的材料时，不猜内容。解释是查询指向什么含义或对象，意图是用户想做什么；同一解释可以有多个意图，同一用户也可能需要多种结果、进行多步搜索。

站在任务语言地区普通用户的角度，包含不同年龄、性别、族裔、宗教、政治倾向等，不以个人喜好或立场代替用户需求。不熟悉查询时，查词典、百科、可信资料或进行网络研究。不要以几个排名靠前的搜索结果界定唯一含义，更不能因结果排在前面就提高评分。充分研究后仍无法理解或专业知识不足时，说明原因并用 unable_to_assess。

| 解释类别 | 判断与作用 |
|---|---|
| dominant：主导 | 大多数用户心中的解释。并非每个查询都有，不能强制指定。 |
| common：常见 | 很多或一些用户会采用的解释；可有多个。 |
| reasonable_minor：合理次要 | 较少用户会采用，但合理、有价值；可能 HM，不自动封顶。 |
| unlikely_minor：不太可能的次要 | 理论上可能，但只有很少用户会如此搜索；有帮助的结果通常 SM。 |
| no_chance：几乎不可能 | 几乎无人会有该解释；即使存在词义联想或关键词，也 FailsM。 |

例如 mercury 的行星／元素可以常见，保险／船用发动机可以合理次要，旧式飞机可以不太可能次要；具体判断仍随时点、地区和查询上下文变化。应认真考虑合理的多样性，不草率排除次要意图；但不能改写查询中的关键限定来“救”结果。

**关键限定：** 地点、时间、人物／实体、属性、行为、否定词、比较对象、版本和条件，都会限定实际需求。非紧急电话不等于紧急电话；有营养要求的蛋沙拉查询不等于任意蛋沙拉；熊能否爬山不等于名为 Bears Ears 的地方登山。结果仅满足某个以后可能需要的步骤，不证明它满足当前查询。

## 2. 用户意图类型

| 类型 | 定义与限制 |
|---|---|
| Know | 了解信息。可以复杂、宽泛、主观、需要探索或多种意见。 |
| Know Simple | 寻找特定、正确、完整且多数人认可的简单事实／信息，通常可用一两句话、短清单或简单图表回答。不是所有问句／是非问句都简单。 |
| Do | 完成活动或目标，例如购买、下载、获得内容、观看、娱乐或使用工具；既可立即完成，也可开放探索。 |
| Website | 去某个特定网站或页面。查询可能是名称、网页描述、完整 URL 或有明显拼写错误的 URL。 |
| Visit-in-Person | 找到可亲自前往的地点、商家或服务，常依赖用户位置。不是所有实体名称都表示要去它的办公室。 |

天气（当前、今日、明日或一周的当地温度及降水等）通常是 Know Simple。股票现价可以 Know Simple，“是否该买这只股票”虽可写成是非问句却通常不是。争议、主观判断、复杂解释、浏览灵感和真实人群观点通常不适合用一个简单事实彻底满足。不要勉强把边界查询唯一归入 Know 或 Do；可记录混合意图。

同一查询可以有 Website 与 Visit-in-Person 双重强意图。例如某零售品牌的官网用于在线购物、预约或获取信息，地点块用于到店；只满足其中一种不能 FullyM。只有一个官网小链接也不一定提供充分的网站访问体验。反之，明确“品牌 website”或具体 careers 页面需求，可能具有单一导航意图。

## 3. 语言地区、用户位置与地图

- locale 指任务语言与国家／地区，不等于用户具体位置。用户位置可能精确、近似或完全未知；以已提供的数据／地图为准。蓝点可能有误差圆，蓝色区域内均可能是用户位置，结果图钉不是用户位置。
- 只在位置会改变用户所需内容时使用它。附近服务、当地法规或最低工资通常依赖地点；固定历史事实通常不依赖地点。
- 查询明确指定位置时，以该指定地点为准，不因为离用户远而降分。例如在加州查华盛顿特定地址，或在 Dallas 查 New York 酒店。
- Visit-in-Person 未指定地点但有用户位置时，位置附近结果通常最有用。“附近”没有统一公里上限：加油站／咖啡店／超市通常需很近，专科门诊、特殊餐厅、图书馆、徒步路线可能接受较远距离，稀缺专业服务可能更远。
- 结合距离、选项、突出程度、营业／服务信息与实际需求判断。不能给所有同城结果同分，不能用世界另一端同类型商家满足本地服务需求。
- 位置也可能创造一种查询解释，例如当地名为 Verbena 的餐厅；但并非任何地方同名商家都因此成为合理意图。缺位置且会显著影响分档时补问／补查；不影响时无需为此停止。

## 4. 时点、含义变化与新鲜度

查询含义随时间变化。未另指定时，产品通常指当前／最新型号，周期性赛事／选举／税表通常指最近、正在举行或临近的一期；当期价格、航班、交通、天气和突发新闻尤其需要当前信息。用户明确历史年份／版本时，以该条件为准，不追新。

需要新鲜内容的查询，只有当前、近期或已更新的内容才支持高 Needs Met。旧事件、旧型号、旧价格或失效指导应降档，已无用则 FailsM；实时交通哪怕只旧一天也可能无用。名人／政治人物查询可以同时有最新新闻和长期人物资料意图，不能把所有旧内容一概判无用。固定历史事实未必需要新文章。

发布时间不等于更新时间，网页显示今天日期也不证明内容最新。必要时核查正文的事实、时间范围或历史快照。历史评测须保持原任务时点，不用今天的事实追溯处罚当时正确内容；历史示例也不是对那些网站当前状态的判断。

**特殊块时延假设：** 天气、股价等为用户展示即时信息的 SCRB，若仅因任务生成到评分之间的延迟显得过期，按用户当时见到的是当前信息处理，除非任务另有指示。此假设不修复错误地点、错误数值或本来已过时的数据；不扩展为普通落地页一律视为最新。

PQ 与新鲜度须分开：准确的历史档案可以高 PQ 却不能满足当前查询；无人维护、内容已错误或误导，则还可能降低 PQ。

## 5. 具体性、产品、URL 与词典结果

- 评分依据对需求的帮助程度，不依据查询与页面的“粒度是否一致”。宽泛类别查询中，热门、突出且有选择空间的品牌／实例可很有帮助；需要时研究当地知名度。宽泛酒店查询的知名连锁首页可能 HM，某偏远单店页可能帮助较少。太具体且不符合实际需求的结果可 SM 或 FailsM，但不是凡“更具体”都降档。
- 产品查询常含浏览、视觉探索、比较、研究和购买前决策，不能假定一定立即在线购买。评测、规格、价格、不同款式／角度的图片、筛选功能等都可能很有用；汽车等最终可能线下购买。明确买、评测、特定官网时应遵循明确意图。产品结果尤其需注意页面质量与交易信任。
- 正常可用的 URL 查询不是只有 FullyM／FailsM 两档。目标网站之外，可信的评价、声誉、近期新闻、相关优惠券、深入介绍都可能对应合理意图；仅提供网站流量或访问统计通常对多数用户无帮助。
- 词典／百科必须看意图。生僻词的定义、明确“是什么／什么意思”或历史背景问题，可适合高分；普通用户早已理解的常见词可能更想要地点、图片、商品等，定义虽相关却可能只 SM。ATM 历史的百科可能 HM，ATM near me 的纯百科则 FailsM。

## 6. 拼写与姓名

明显误拼／误输入按实际意图评价，例如 federal expres、new england patroits、www.netflix.coom。不是明显误拼则尊重原写法，先研究再判断；不要自动改成最知名的相似名字。

john stuart 不应一律当作 Jon Stewart；micheal jordan 有真实同名者，Michael Jordan 在这一例中只是不太可能的次要解释。对准确拼写的人名，相关更突出人物的有帮助结果可比极不知名同名者更有用；但名气不能取消其他人的存在，更不能自动产生 FullyM。
